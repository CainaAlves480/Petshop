Como foi feito e o que o código faz

Da modelagem no PostgreSQL até a tela: cada camada tem uma responsabilidade clara

SLIDE 3

Como foi feito

1Modelagem: script.sql criou 8 tabelas, chaves, FK, CHECK, índices e dados de exemplo.
2Regras no banco: Function calcula totais, Procedure finaliza vendas e Trigger audita estoque.
3API: Express expôs rotas REST; controllers validam dados e usam SQL parametrizado com pg.
4Interface: páginas HTML/CSS/JS consomem a API com fetch, modais, tabelas e indicadores.
5Validação: SQL executado, rollback testado e API verificada em http://localhost:3001.

O que o código faz

Fluxo de uma requisição

tela → rota /api → controller → pg.query($1...) → PostgreSQL → JSON → tela

Fluxo da venda

  • POST /api/vendas cria a venda pendente.
  • POST /:id/itens pega o preço do produto e recalcula com calcular_total_venda.
  • POST /:id/finalizar executa CALL finalizar_venda no banco.
  • A procedure valida estoque: sem estoque → ROLLBACK; com estoque → baixa, trigger registra, total salvo e COMMIT.
  • O frontend recarrega lista e detalhes, mostrando o resultado ao usuário.
Resumo: a interface envia intenções; a API traduz para SQL seguro; o PostgreSQL garante integridade, transação e auditoria.
Notas do apresentador
  1. Primeiro foi modelado o banco em script.sql: tabelas, chaves, checks e dados de exemplo.
  2. Depois vieram as regras no PostgreSQL: function, procedure com transação e trigger de auditoria.
  3. O backend Express recebe requisições, valida parâmetros e envia SQL parametrizado pelo pg.
  4. O frontend apenas consome a API com fetch e atualiza a interface.
  5. No fluxo da venda: criar venda, adicionar itens com preço vindo do produto e finalizar chamando a procedure.
  6. Reforce que rollback e commit acontecem no banco, não no JavaScript.
  7. Feche com: interface envia intenções, API traduz para SQL seguro, PostgreSQL garante integridade.
